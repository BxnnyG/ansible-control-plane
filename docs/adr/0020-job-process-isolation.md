# ADR-0020: Job process isolation in the worker

- Status: accepted
- Date: 2026-11-07

## Context
Security review finding F-02: the worker container ran `acp worker` and the spawned `ansible-playbook` under the same uid (10001). The worker token (`/run/secrets/worker_token`, owned by 10001, mode 600 because the app container reads the same file as 10001) was therefore readable by any playbook, as were `/proc/<worker>/environ` and `mem`. The token claims any run of any workspace including its secret bundle, so a malicious or compromised project could pull other workspaces' secrets. Related: L-05 (symlinks in a project tree could point at files outside it) and run params returned unmasked to viewers.

## Empirical constraints (Docker 29.7.2, kernel 7.0, checked on the host)
- `user: 10001` plus `cap_drop: [ALL]` plus `cap_add: [SETUID, SETGID]` yields CapBnd = those caps but **CapPrm, CapEff and CapAmb all empty**. A non-root container user gets no usable and no ambient capabilities from `cap_add`, so "start as 10001 with ambient caps" (candidate a) does not work in plain compose.
- File capabilities (`setcap cap_setuid,cap_setgid+ep`) on a binary **do take effect** with `no-new-privileges:true` (NoNewPrivs=1 confirmed in `/proc/self/status`) as long as the capabilities are in the bounding set. So compose `cap_add` sets the ceiling and the file capabilities grant them to exactly one binary.
- After the supervisor switches a child to another uid and execs a normal binary, the child has empty permitted/effective/ambient sets (no inheritable/ambient bits are set), so a job never keeps the supervisor's capabilities.

## Decision
- **Chosen design (a variant of a):** the container still starts as uid 10001 with `read_only`, `no-new-privileges` and `cap_drop: [ALL]`, plus `cap_add: [SETUID, SETGID, CHOWN, KILL]`. The supervisor binary is a separate copy `/usr/libexec/acp/acp-worker` (mode 0750, `root:acp`, in a 0750 directory) carrying file capabilities `cap_chown,cap_kill,cap_setgid,cap_setuid+ep`; it is the image entrypoint. `/usr/local/bin/acp` is a capability-free copy. Job users cannot execute the capability-carrying binary, otherwise they could regain SETUID. No launcher process and no root process exist. Rejected: ambient caps from compose (not granted), a root launcher (extra process with CAP_SETUID that must also be able to read the 10001-owned token, which needs DAC capabilities).
- **Job identity:** one job user per concurrency slot, uid = gid = `ACP_WORKER_JOB_UID_BASE` + slot (default 10100, image has `acpjob0..15` for ssh, which rejects uids without a passwd entry). `ansible-playbook` and `ansible-galaxy` are started with `SysProcAttr.Credential` (uid, gid, no supplementary groups) in their own process group. Per-slot instead of one shared job uid so concurrent runs of different workspaces cannot read each other's SSH keys, vault files or `/proc` entries. Different uids already block ptrace and `/proc/<pid>/{environ,mem}` of the supervisor; the capability-carrying binary is additionally non-dumpable.
- **Run directory:** the supervisor creates and fills it as 10001 (mode 0700 tree), then hands it over: the directory itself stays supervisor-owned (0710, group = job gid, so only that job traverses), everything below is chowned to the job uid (keeping 0600 for key files; ssh needs that). `project/` and `events.jsonl` keep the group `acp` with group read so the supervisor can read requirement files and tail callback events. `/tmp/runs` is 0711. `HOME` of a job is `<run dir>/tmp/home`. After the process group ended (SIGKILL to stragglers of the group) the supervisor takes the tree back (chown to itself, top-down, via `os.Root` so nothing outside is touched) and removes it; a job-made directory with mode 000 is therefore still removable.
- **Galaxy cache:** installed as the job user into a temporary directory, taken over by the supervisor and published world-readable but not writable (cache dirs 0711 on the way), so a job cannot modify cached collections of other runs.
- **Fail closed:** with `ACP_WORKER_JOB_UID_BASE` set (the image default) the worker refuses to start unless CAP_SETUID, CAP_SETGID, CAP_CHOWN and CAP_KILL are effective. `ACP_WORKER_JOB_UID_BASE=0` runs jobs under the worker uid for development and logs a warning.
- **L-05:** bundle extraction rejects symlinks outside `project/`, absolute targets and targets that climb out of `project/`; after extraction every symlink is resolved for real (chains included) and must stay inside the project; the playbook path is resolved the same way. Links created later by a playbook are covered by the uid separation, not by this check.
- **Run params:** run API responses (list, detail, start, cancel, run list stream) mask `extra_vars`, `env_vars` and override variable values for roles without `template.write`, reusing the placeholder of the template API.

## Consequences
- The worker container needs four capabilities, but only the supervisor process holds them; jobs hold none. Verified by the e2e test: a playbook asserts it runs as a job uid, has zero capability sets, cannot read the token file, `/proc/1/environ` or `/proc/1/mem`, cannot `setuid(10001)`, cannot execute the supervisor binary and cannot list `/tmp/runs`.
- The mechanism depends on the kernel honouring file capabilities under no-new-privileges (true on the tested kernel, documented kernel behaviour for caps within the bounding set). The startup check turns a different behaviour into a clear start-up error instead of silent non-isolation.
- Residual risks: a job can still reach everything the egress network allows (F-04, separate step); a process that escapes the process group (setsid) can outlive the run and keeps its uid until the container restarts (no CAP_KILL sweep over all of the uid); concurrency above 16 is not allowed by the config anyway.
- Follow-up (not implemented): per-worker claim scoping. The worker token still claims any queued run; with a single worker this adds nothing, but with several workers the app should bind claims to a worker identity and restrict bundle/event routes to the claimant's lease (internal/workerapi handler).
